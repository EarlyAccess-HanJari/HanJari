# 2026-11-02 차량 갱신·수집 장애 운영 수정

현재 활성 릴리스는 **`recovery-20261102-v1`**이다. 프론트 제안을 즉시 적용하라는 뜻으로 잘못 해석해 추가했던 화면 변경을 철회하고, 소스·문구·입력창·배포 파일을 **`8e7e96f`의 기존 구성 그대로 복원**했다. 이번 추가 작업은 호출 장부 복구와 저장 자료 내부 검사로 한정한다. 앞서 적용한 차량 갱신·오래된 데이터 차단은 유지하며, 카드 미태그 후보를 사용자 표시값에서 차감하지 않는다.

종로03 창신역4번출구에서 화면의 53명과 실제 탑승 차량 약 21명이 달랐다는 신고를 조사했다. 저장 자료에서 53~54명은 앞차 5508, 이후 첫 도착 차량으로 바뀐 3170은 22명이었다. 두 차량의 정류장 위치 보고는 약 50초 차이였다. 사용자 화면의 당시 HTTP 응답은 보존되어 있지 않으므로 신고 시각·탑승 차량의 정확한 일치까지 입증한 것은 아니다.

수정 전 서버는 도착·위치의 동일 수집 시각을 기다리며 최신 도착 정보를 놓칠 수 있었고, 화면은 수집 시각으로 ETA를 다시 계산하여 공급 시각과의 차이만큼 늦어졌다. 가까운 버스도 30초 간격으로 갱신했고 만료된 ETA를 계속 ‘곧 도착’으로 표시할 수 있었다. 운영 예측 코드는 10월 버전으로, PR의 앞선 수정이 적용되어 있지 않았다.

## 적용 내용

- 노선별 최신 도착 응답을 선택한다. 위치 수집 지연, 다른 노선 장애, 자정의 빈 폴더 때문에 최신 버스를 놓치지 않는다. 정상적인 API ‘결과 없음’(코드 4) 뒤에 지난 버스를 복원하지 않는다.
- 동일 차량 ID·번호의 더 최신 위치로 통과가 확인되면 다음 차량의 전체 정보를 선택한다. ETA는 공급 시각에 고정하고, 만료되면 인원·확률을 지운다. 근접 차량은 서버 저장 자료를 5초마다 확인한다. 추가 서울시 API 호출은 없다.
- 오래되거나 충돌하는 차내 인원은 서버부터 `null`로 내린다. 정상적인 최신 API 인원은 ‘추정’으로 표시한다. 현장 검증이 없는 탑승 확률은 숫자로 내보내지 않는다.
- 수집기는 실패한 요청도 전송 전에 키별·서비스별 장부에 기록한다. 재시작해도 사용량을 되돌리지 않는다. API 실패 시 재시도를 최대 5분까지 늦추며, 살아 있는 수집기를 외부 장애 때문에 반복 재시작하지 않는다.
- `/api/health`는 서버 생존과 데이터 갱신 상태를 구분한다. `/api/predict`는 날짜·출처 시각·상태와 `no-store`를 반환한다. 데이터 부족을 운행 종료로 안내하지 않는다.
- 기존 운영 PWA의 설치 안내·아이콘·manifest·오프라인 화면·연결 복구 시 즉시 갱신을 보존했다. SW는 API 응답을 저장하지 않는다. 이전 해시 자산도 운영에 남긴다.

## 운영 확인과 남은 외부 조건

초기 수정본을 `2026-11-02T13:35:33Z`(22:35 KST)에 운영 반영했다. 이후 r2에서 기존 화면도 지연 상태를 알아보도록 응답 호환 처리를 추가했다. 23:24에 반영했던 화면 구성 변경은 철회했다. 현재 릴리스는 `/home/ubuntu/hanjari-releases/recovery-20261102-v1`이며 프론트 배포 파일 13개가 r2 및 커밋 `8e7e96f`와 SHA-256 기준으로 일치한다. 수집기는 v2 장부를 유지하며 이번 화면 복구 과정에서 재시작하지 않았다. 이전 릴리스들과 원본 보관 `/home/ubuntu/hanjari-backups/freshness-20261102-2235-KST`를 남겼다.

운영 로그에는 18:26 KST부터 HTTP 503이 나타났다. 마지막 도착 자료는 종로03 18:35:06, 성북02 18:36:00이다. 운영 서버와 별도 작업 서버에서 인증키 없이 같은 경로를 호출해도 503이 나왔다. 특정 키 오류나 앱 파싱 오류만으로 설명되지 않는 외부 API 경로의 장애이며, 제공사 내부 원인까지 확인한 것은 아니다. HTTPS 대체 요청도 연결되지 않았다.

기존 수집기는 성공 파일만으로 호출 횟수를 복구하면서 18:50~22:10에 여러 번 재시작했다. 22:35 배포의 장부 초기화도 잘못 보수적이었다. 저장 성공과 실패를 합친 서비스별 3,869회를 4개 키로 나눈 평균 967.25에 반올림·임의 여유분을 더해 **992회**로 기록하고 수집을 막았다. 이 수치는 제공사 실사용량이나 한도 초과 확인값이 아니며, 503 원인을 입증하지도 않는다.

이를 수정해 **23:13:25 KST에 수집을 재개**했다. 과거 라운드로빈의 재시작·일자 초기화 구간을 재생하여 키당 서비스별 기록 범위 **965~970회**, 구간 끝 미기록 가능량 **9회**, 확인된 별도 진단 요청을 분리했다. 새 전송 예약은 별도 필드에 누적하고, 재시작해도 되돌리지 않는다. 기존 장부는 `.before-reconcile`로 보관했다. 내부 상한 990회는 유지하고, 한 키의 예산이 없으면 남은 키를 확인한다. 추정 상한에 도달한 경우와 실제 예약량 소진도 구분한다. 재개 후 요청이 실제 발생했지만 HTTP 503은 계속되어 도착 자료는 아직 갱신되지 않았다. 자정은 장부의 날짜 경계이며 외부 장애 해소를 보장하지 않는다.

23:46 KST 재확인에서 공식 도착 API 경로는 인증키가 없는 요청에도 503 HTML을 반환했고, 같은 호스트의 루트 경로는 응답했다. 공공데이터포털의 요청주소와 현재 수집기 주소는 일치한다. 이는 HTTP 단계 실패의 증거이며 제공기관 내부 원인이나 계정 한도 초과를 입증하지 않는다. 정상 인원 데이터를 제공하는 독립 대체 출처는 확인되지 않았으므로 검증되지 않은 주소로 자동 전환하지 않는다.

23:53:47 KST에 수집기 진단을 보강했다. 모든 예외를 외부 오류로 묶던 처리를 바꿔 요청·응답 해석·API 헤더·파일 저장·시간표 처리 단계를 구분하고, HTTP 상태와 제공사 응답 코드를 따로 기록한다. 오류 응답은 형식·최대 8 KiB 지문만 남기며 URL·키·원문 메시지는 기록하지 않는다. 복구 후 이전 오류 정보도 제거한다. 실패 요청 예약·재시도 간격·호출 상한은 유지했다. 운영 수집기 두 사본만 교체했으며 웹 재시작·프론트 변경은 하지 않았다. 배포 기록은 `/home/ubuntu/hanjari-collector-releases/diagnostics-20261102-v1/deployment.json`이다.

23:55 KST의 실제 인증 요청에서도 두 노선·두 서비스 모두 `failure_stage=request`, HTTP 503, HTML 192바이트가 기록됐다. 오류 본문 지문은 앞선 인증키 없는 응답과 일치했다. JSON 파싱·내부 저장 단계가 원인이 아님을 확인했으며, 제공기관 내부 실패 원인까지 알아낸 것은 아니다.

[외부 장애 재현 근거와 문의 초안](../hanjari-ml/reports/upstream_incident_20261102.json)을 준비했다. 문의는 발송하지 않았다. 원천 503 해소와 카드 집계 인원의 실제 정확도는 여전히 별도 확인이 필요하다.

## 카드 미태그·저장 자료 내부 검사

`quality_audit.py`는 외부 API 호출 없이 저장된 응답에서 인원 형식·충돌·차량 전환·같은 차량의 큰 인원 변화와 종점 차감 가정을 검사한다. 큰 변화는 실제 승하차일 수도 있으므로 오류로 단정하지 않는다. 낙산공원 후보는 동일 차량 ID·번호·회차 안에서만 추적하며, 다음 회차·날짜 변경·관측 공백·API 인원이 후보보다 낮아지면 차감 가정을 폐기한다. 성북02는 빈 차 구간이 확인된 종점 조건을 아직 등록하지 않았다.

4일 고정 자료에서 낙산공원 조건을 만족한 관측 구간 90개 중 양수 후보는 5개, 1~3명이었다. 이후 API 인원이 후보보다 낮아져 차감 가정을 폐기한 사례도 1개 있었다. 따라서 고정 차감은 중복 보정 위험이 있다. 90개는 독립 운행 수가 아니며 후보를 미태그 확정 인원으로 보지 않는다. [일별 집계](../hanjari-ml/reports/quality_review_20261102.json)에 입력 지문·부분일 마감을 남겼다.

`hanjari-quality.timer`를 설치해 매일 **00:50 Asia/Seoul**에 전날 자료를 검사한다. 네트워크 접근은 차단했고 원본·학습·표시값은 바꾸지 않는다. 결과는 `/home/ubuntu/hanjari-ml/reports/source-quality/YYYYMMDD.json`에 저장한다. 수동 실행으로 23:26:16 KST에 전날 보고서가 생성되고 서비스 종료 코드 0을 확인했다. 이 결과는 API 내부 일관성 검사이며 실인원·탑승 성공률 검증은 아니다.

## 배포 범위·복구

웹은 릴리스 폴더의 소스·설정·모델 사본을 사용한다. 수집 원본은 기존 위치를 읽는다. 기존 학습 소스/학습 작업/원본 데이터/환경 키는 수정하지 않았다. 종전 일일 학습이 만드는 모델은 이 검증 보류 릴리스에 자동 반영되지 않는다. 운영 ML 폴더에서는 수집기와 감시기의 장애 처리 파일을 갱신하고 품질 보고서 폴더를 추가했다. 새 검사 작업은 `/home/ubuntu/hanjari-quality`가 가리키는 릴리스 소스로 실행한다.

실제 활성 릴리스는 `systemctl show hanjari-web -p WorkingDirectory`와 `/api/health`의 `release`로 확인한다. 전환 설정은 `/etc/systemd/system/hanjari-web.service.d/20261102-freshness.conf`다. 웹 장애 시 r2의 `web-service.conf`를 drop-in으로 복원하고 frontend `dist` 심볼릭 링크를 r2의 dist로 돌린 뒤 `daemon-reload`와 웹 재시작으로 복구할 수 있다. 철회한 `counts` 화면으로는 돌아가지 않는다. 내부 검사만 중지하려면 `hanjari-quality.timer`를 비활성화한다. **v2 호출 장부를 구버전 수집기에 넘기거나 원본 장부를 되돌리면 안 된다.** 수집기 복구는 v2 장부를 읽는 버전으로 수행한다. 수집 데이터·모델 원본·보관본은 덮어쓰지 않는다.

GitHub main 병합과 운영 긴급 수정은 별개다. PR #7은 팀 검토를 거쳐 병합하며 리뷰를 우회하지 않는다.
