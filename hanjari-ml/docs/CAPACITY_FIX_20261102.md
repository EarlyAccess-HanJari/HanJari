# 2026-11-02 종로03 인원 불일치 조사와 수정

종로03에서 실제로 센 인원은 21명인데 서비스에서는 50명 이상이었다는 제보를 조사했습니다. 제보의 정확한 시각·차량은 없어 동일 사건의 실인원 오차를 재현하지 못했습니다. **이번 변경은 원본 API를 21명으로 보정한 결과가 아닙니다.** 확인된 코드 결함을 수정하고, 현장 검증이 없는 인원·확률 안내를 차단합니다.

## 원본에서 확인한 사실

2026-10-30~11-02 18:30 KST 이전 고정 로그 29,827개를 운영 서버에서 읽기 전용으로 회수했습니다. 차량 관측의 마지막 시각은 11-02 18:28:48 KST입니다. JSON 파싱 오류는 없고 API 오류 응답은 89개였습니다. API를 새로 호출하거나 운영 파일·서비스를 변경하지 않았습니다.

## 원인 구분과 코드 변경

1. **관측 최댓값을 정원으로 사용:** `max(잠정 정원, API 관측 최댓값)`이 높은 API 인원을 더 큰 차량 정원으로 해석했습니다. 이를 제거하고 점·분위수 예측의 정원 상한 클리핑도 제거했습니다.
2. **차종 코드와 정원의 혼동:** `busType`은 0=일반, 1=저상, 2=굴절입니다. 소형/대형이나 정원이 아닙니다. 기존 33·55명은 오프라인 API 대리지표의 잠정값으로만 남기고 서비스 허용 근거에서 제외했습니다.
3. **결측을 0명으로 학습:** `rerdie_Div=0`의 `reride_Num=0`을 빈 버스로 취급할 수 있었습니다. 마을버스(`routeType=2`)·인원형(`rerdie_Div=2`)·음수가 아닌 정수만 인원으로 읽습니다. 혼잡도형(4), 잔여좌석 의미의 광역버스(6)는 인원으로 사용하지 않습니다. 둘째 버스·노선 평균·학습 정답에도 동일 검사를 적용합니다. 성북02의 129개 기록은 실제 원본에서 이 결함을 확인한 근거이며, 종로03 제보의 직접 원인으로 주장하지 않습니다.
4. **제공 시각·차량·상충값 검사 누락:** 180초 초과·5초 초과 미래·미상 시각, 차량 ID 불일치, 같은 차량의 상충 인원을 학습/예측에서 제외합니다. 위치 피처도 위치 시각을 검사합니다. 높은 수치나 큰 증감만을 이유로 임의 보정하지 않습니다.
5. **재학습으로 안내가 다시 열리는 경로:** 모델 메타데이터와 별개인 `config/boarding_policy.json`에 현장 검증 승인과 차량별 정원 근거를 둡니다. 기본은 `enabled=false`, 차량 목록은 비어 있습니다. 재학습은 이 설정을 바꾸지 않습니다. 모델 정책은 데이터 스키마·정원표·차량 ID별 정원까지 비교합니다. 안내 기준 보정에는 확인된 차량·수업일·보류하지 않는 구간 폭의 행만 사용하며, 미확인 차량을 잠정 정원으로 평가한 성적은 서비스 기준에 섞지 않습니다.
6. **화면에서만 숫자를 숨김:** 보류 시 `load_pred`, `load_10`, `load_90`, `p_board`를 API에서도 `null`로 반환합니다. `r_now`는 원본 추적용이며 인원형이 아니면 `null`; 화면에서는 모든 보류 인원을 숨깁니다. 입력 불량 행에는 모델을 실행하지 않습니다.
7. **불완전한 스냅샷·옛 캐시 재사용:** 노선별 도착·위치 응답이 모두 정상인 가장 최근 동일 시각 묶음을 사용하고, 각 노선의 수집 시각을 별도로 검사합니다. 묶음 자체가 없으면 503입니다. 이전 데이터셋 스키마는 학습을 거부하며, 압축된 옛 원본이 필요한 경우 복구 전에는 캐시를 덮어쓰지 않습니다.

API 필드 의미는 [공공데이터포털 공식 도착정보 명세](https://www.data.go.kr/data/15000314/openapi.do)를 기준으로 확인했습니다. 서울시가 설명한 마을버스 혼잡정보는 교통카드 승하차 기반이지만, 이를 이번 21명 대 50명 이상의 불일치 원인으로 확정할 수 없습니다. [서울시 안내](https://news.seoul.go.kr/traffic/archives/510878).

## 왜 기존 검증에서 발견하지 못했나

학습 입력의 현재 인원과 정답인 도착 인원이 모두 같은 API에서 나왔습니다. API가 실제보다 크게 집계하면 모델은 그 큰 값을 잘 예측해도 오프라인 오차가 작게 나올 수 있습니다. 실제 탑승 여부도 직접 기록하지 않고 `API 도착 인원 <= 정원 - 앞 대기 인원 - 1 + 평균 하차`로 만들어 평가했습니다. 여기에 관측 최댓값으로 정원을 늘리는 계산이 결합해 높은 인원을 받아도 '탑승 가능' 정답이 생겼습니다. 기존 '실제 탑승률'이라는 표현은 이 차이를 가렸고, 이번에 API 기준 대리지표로 정정했습니다.

결함 설명용으로 API 도착 인원 53명, 앞 대기 10명, 평균 하차 2명을 가정하면 관측 최댓값 정원 71에서는 기준이 `71 - 10 - 1 + 2 = 62`여서 가능으로 분류됩니다. 잠정값 55를 쓰면 기준은 46으로 바뀝니다. **55가 실제 차량 정원이라는 뜻은 아닙니다.** 그래서 숫자 하나를 바꾸는 데 그치지 않고 확인된 차량 정원과 현장 대조를 서비스 재개 조건으로 분리했습니다.

응답 JSON 형식과 차량 ID가 정상이어도 실제 승객 수의 정확성까지 보장되지는 않습니다. 종로03 원본의 과대 여부·원인을 확정하려면 같은 시각·차량의 현장 인원과 대조해야 합니다. API가 교통카드 기반이라는 설명만으로 하차 미태그, 집계 지연 또는 특정 계산 오류를 이번 사건의 원인으로 단정하지 않습니다.

## API와 화면 계약 변경

프론트엔드·API 변경을 함께 검토/반영해야 합니다. 기존 보류 응답의 숫자도 프론트에서 숨겨 이전 버전과의 교체 중 표시를 방지합니다.

- `r_now`: 정수 또는 `null`. 실제 센 인원이 아니라 API 제공 인원입니다.
- `load_pred`, `load_10`, `load_90`, `p_board`: 보류일 때 모두 `null`. `null`을 0으로 바꾸지 않습니다.
- `data_status`: 원본 입력 상태. `ok`, `passenger_unavailable`, `passenger_conflict`, `source_stale`, `source_time_unknown`, `vehicle_unknown`, `vehicle_mismatch`.
- `prediction_status`: 보류 원인 또는 `ok`. 현장 미검증, 차량 정원 미확인, 모델 정책 불일치, 정원 초과, 수집 지연, 기존 요일/데이터 부족 보류 등을 구분합니다.
- `arrival_stale`: 도착 안내를 사용할 수 없는 시각 상태. 프론트가 한국어 설명 문구를 분석할 필요가 없습니다. 인원 결측과 별도로 판단합니다.
- `updated_at`: 날짜·KST 시간대가 포함된 수집 시각. `updated`도 기존 호환을 위해 유지합니다.
- `source_updated`: API 응답의 제공 시각이며 인원 자체의 갱신 시각이 아닙니다. `vehicle_id`는 정원 등록/원본 대조에 사용합니다.

정상 도착 정보는 인원 예측 보류 중에도 유지합니다. 잘못된 응답 타입·음수·범위 밖 확률·보류인데 수치가 있는 새 계약 응답은 프론트에서 오류 안내로 처리합니다.

## 검증과 운영 반영

- Python 회귀 검사 32개 통과: 결측/진짜 0명, 둘째 버스, 차량 불일치, 상충값, 원본 시각, 노선별 지연, 구캐시 보호, 정원 정책, 재학습과 독립적인 보류 조건, 확률 단조성.
- `serve.py check` 통과: 실제 샘플과 포함 모델, 동시 요청 검사. Python 소스 전체 구문 검사 통과.
- 프론트엔드 `build:prod` 통과. 기존 목업 Playwright 68개, 실제 fetch 경로/응답 검증 Playwright 8개 통과(모바일·PC). 소스 lint 오류 없음, 기존 LevelBadge Fast Refresh 경고 1개.
- 실제 FastAPI 샘플 서버와 프로덕션 빌드를 연결해 6개 정류장 null 계약, -1·41명 입력 400 응답, 393px·1280px 화면의 보류·도착 안내를 확인했습니다.
- 4일 원본에서 학습 행 39,871개(성북02 19,941 / 종로03 19,930)를 재생성했습니다. 10-30~31로 학습하고 11-02 8,746행을 예측해 유한 결과와 대기 인원에 따른 확률 단조성을 확인했습니다. 이는 파이프라인 실행 검사이며 현장 정확도나 배포 성능 검증이 아닙니다. [재생 검사 기록](../reports/replay_check_20261102.json).

기존 모델 파일과 운영 서버는 변경하지 않았습니다. API의 실인원 정확도와 탑승 성공률이 회복됐다고 주장하지 않습니다.

서비스 확률을 재개하려면 다음 순서가 필요합니다.

1. 차량·시각별 실제 인원과 API를 대조하고, 대상 차량의 승차 정원을 근거와 함께 확인합니다. 제보의 특정 시각/차량이 확인되면 원본 기록과 연결합니다. 실제 탑승 성공/실패와 API 계산 정답을 별도 관리합니다.
2. `config/boarding_policy.json`의 `vehicles`에 `route`, `plate`, `vehicle_id`, `capacity`(확인된 정수), `evidence`(확인 자료 경로/링크)를 기록합니다. `enabled`는 아직 false로 둡니다.
3. 원본 archive를 별도 작업 공간에 복구하고 새 규칙으로 데이터셋을 재생성합니다. 기존 schema 없는 CSV/날짜 캐시를 재사용하거나 버전 번호만 붙이지 않습니다. `daily.py`는 원본이 없는 구캐시 마이그레이션을 자동 우회하지 않습니다.
4. 새 데이터·확인 정원으로 날짜 분할 검증과 모델 export를 수행합니다. 현장 정확도 검증은 이 API 기반 검증과 별도로 완료하고 `validation_evidence`에 근거를 기록합니다. 메타데이터만 수동 변경해 우회하지 않습니다.
5. 팀 검토 후 `enabled=true`로 전환합니다. 등록되지 않은 차량은 계속 보류됩니다. 설정이 누락·손상되거나 정원표가 달라진 모델은 보류됩니다. 긴급 중단은 false로 되돌리면 되며 모델 재학습이 필요하지 않습니다.

기본 설정으로는 **새 모델을 만들어도 확률이 계속 보류됩니다.** 운영 배포·병합은 팀 검토 후 별도로 진행합니다. 기존 PR #6의 보류 완화 실험은 이전 정원 정책에 의존하므로 보류 상태이며 새 기준으로 재평가해야 합니다.
