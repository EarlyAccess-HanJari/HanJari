# AI/데이터 설계 (초안, 2026-09-23)

## 1. 왜 이 구조인가
- "이 버스에 탔나/못 탔나" 정답은 공공데이터에 없음 → 원래 계획은 사람이 관측(WBS 1.5, 2.2).
- 관측은 인력 부담이 크고 매일 값이 달라 현실적으로 불가 → **정답이 자동으로 생기는 문제로 바꾼다.**
- 탑승 실패는 "남은 자리보다 내 앞 대기 인원이 많을 때" 발생 → 남은 자리만 예측하면 됨.
  남은 자리를 결정하는 재차인원은 공공데이터/API에서 얻을 수 있음.

## 2. 분해
```
입력(조회 시점): 요일, 시각, ETA(첫째 버스), 남은 정류장 수, (있으면) 그 시점 재차인원/혼잡도
        │
        ▼
[모델] 입구역 도착 시 재차인원 R 의 분포 추정   ← 학습 대상
        │
        ▼
[규칙] 남은 자리 S = C − (R − 입구역 하차 D)
       P(탑승) = P(S > 앞 대기 인원 N)           ← N은 사용자 입력
```
- C(정원): **잠정값 = 법정 정원 + 10** (지용 결정 09-23, 실제로 입석을 더 태우므로).
  - 작은 차(7m, 뉴카운티급, busType=0 추정): 법정 21~23 → **C=33**
  - 큰 차(하이퍼스1609P 9.6m 저상, busType=1 추정): 1609P 법정값 미확인, 10.5m 기본형 45 사용 → **C=55** (과대 가능)
  - 수집 데이터의 busType별 피크 최대 reride_Num 이 쌓이면 그 값으로 교체.
- D(입구역 하차): CSV 시간대별 하차 ÷ 운행횟수로 평균 사용 (초기엔 상수 취급 가능).

## 3. 단계별 모델
| 단계 | 데이터 | R 추정 방식 | 역할 |
|---|---|---|---|
| 0 | CSV만 | 요일·시간대별 평균 (±일별 변동) | 기준 모델. API 없어도 동작 |
| 1 | API 자동 수집 로그 | XGBoost 회귀/분위수 회귀 | 후보 모델. 기준 대비 개선 확인 |
| 2 | (선택) LightGBM/CatBoost | 동일 | OSS 비교 (PRD 요구) |

- 분포가 필요하므로 점추정만 하지 말 것: 분위수 회귀, 또는 잔차 분포로 구간 추정.
- 평가: R 예측 오차(MAE 등) + 최종 P(탑승)의 보정 상태. 지표·공개 임계값은 팀 합의 필요(미정).

## 4. 실시간 API 자동 수집 (정답 자동 생성)
- 등교 시간대에 N초 간격으로 성북02 도착정보 조회 → 원본 응답 그대로 저장(`data/api_logs/`).
- 차량번호(vehId/plainNo)로 같은 버스를 추적:
  - **X**: 조회 시점 스냅샷 (ETA, 남은 정류장, 그 시점 재차인원)
  - **y**: 그 차량이 입구역에 도착한 직전/직후 스냅샷의 재차인원
- 전제: 성북02에 재차인원/혼잡도 값이 실제로 나와야 함 (TASKS 2에서 확인).
  - 3단계 혼잡도만 나오면 y가 범주형 → 분류로 바꾸고 C 환산은 대략적.
  - 아예 안 나오면 단계 1 불가 → 단계 0 + 도착정보 중심 MVP로 축소 (PRD의 "예측 보류" 허용 범위).

## 5. 최종 검증
- 규칙 부분(C, D, N → 탑승 여부)은 API로 검증 불가 → 11주차 독립 평가 때 **며칠만 소량** 실제 탑승 여부 확인 (정규 관측 아님).

## 6. WBS 변경 제안 (팀 합의 필요)
- 1.5 / 2.2 "정규 관측" → "API 자동 수집기 운영 + 데이터 품질 점검"
- 1.8 "관측 데이터 전처리" → "CSV·API 로그 전처리"
- 1.9 기준 모델 → CSV 시간대별 평균 재차인원
- 범위 → 등교 방향만 (PRD·WBS 문구 수정)
