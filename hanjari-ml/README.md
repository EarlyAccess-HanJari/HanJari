공공 API에는 실제 탑승 성공·실패 정답이 없습니다. **학습 정답은 API 도착 인원으로 자동 생성**하고, 실제 탑승 평가는 11/9~11/13 전원 등교 기록으로 별도 수행할 예정입니다.

```
탑승 가능 ⇔ 남은 자리 > 내 앞 대기 인원
남은 자리 = 정원 C − (도착 때 재차 y − 그 정류장 하차 D)
P(탑승) = P( y − D ≤ C − N − 1 )        N = 내 앞 대기 인원(사용자 입력)
```
- **모델이 맞히는 것 = 버스가 내 정류장에 도착했을 때의 재차 인원 y 의 분포.**
- y 는 서울시 버스 API 가 주는 재차 인원(`reride_Num`)이라, 버스가 도착할 때마다 정답이 자동으로 쌓입니다.
- 정원 C: `config/boarding_policy.json`에 등록한 차량별 **API 기반 실용 정원**(성북02 일반 38·저상 60, 종로03 일반 52·저상 54). 혼잡 시간 붐비는 정류장에서 탑승 한계 추정값과 출발 인원 상위 1%로 정함. 실제 탑승 한계와의 일치는 현장 검증 전([근거](docs/PRACTICAL_CAPACITY_20261104.md), `src/exp_practical_capacity.py`). `busType`은 일반/저상 구분일 뿐이고, 관측 최대로 정원을 올리지 않습니다.
- 하차 D: 공공 CSV 의 시간대별 평균.

## 5. 모델

**구조: 규칙 + XGBoost 가 규칙의 오차를 학습**
```
규칙   = 지금 재차 + 남은 정류장들의 과거 평균 순승차(CSV) + 지금 정차 중인 정류장의 미반영 몫
예측 y = 규칙 + XGB(피처)          ← XGB 는 "규칙이 얼마나 틀리는지"만 배움
```
- **점 예측**: 절대오차(MAE) 목표 XGB.
- **확률**: 5~95% 분위수 9개를 한 번에 내는 XGB → 그 분포로 P(탑승) 계산.
- **바로 앞(0정류장 전)**: 버스가 그 정류장에 서 있으면 재차가 아직 안 바뀐 상태(재차는 **출발할 때** 갱신됨) → 전용 작은 모델 + 실제 오차 분포.
- 설정: 깊이 5 · 트리 300 · 학습률 0.06, **수업 있는 날(월~토, 공휴일 제외)만 학습** (과거 09-30~10-01 측정: 깊이 2→5, 평일만 MAE 3.09→2.84, 서버 1GB 에 맞춰 가볍게: 정확도 같고 학습 메모리 609→472MB·예측 722→406MB).
- 재차 예측은 0 이상으로만 제한합니다. 잠정 정원에서 잘라 인원 초과나 예상 범위를 숨기지 않습니다.

**라이트 모델 (이 레포의 `models/lite/`)** — **한 시점의 API 스냅샷 묶음**에서 계산되는 피처를 씁니다. 운영 조회는 저장 자료를 재사용하며, `live` 실행만 외부 API 4건을 호출합니다.

| 묶음 | 피처 |
|---|---|
| 위치·재차 | 몇 정류장 전, ETA, 지금 재차, 차종·정원, 채움 비율 |
| 뒤차 | 둘째 버스 ETA·재차, 두 버스 간격 |
| 노선 전체 | 지금 노선 위 모든 버스 평균 재차 |
| 과거 평균 | 남은 구간 CSV 평균 순승차, 하차, 이전 수집일 같은 시간대 실측 |
| 수업 | 버스 도착 10~35분 뒤 시작하는 강좌 수, 다음 큰 수업까지 분, 수업 직전 여부 |
| 달력 | 요일, 학기/방학, 시험, 공휴일 |
| 위치 API | 정차 중인지, 구간 진행률, 정차 중 미반영 몫 |

오라클 수집 이력(최근 60~90분 다른 버스들의 승차 흐름 등 10개)까지 쓰는 **전체 모델과 오차가 비슷했던 과거 실험**이 있습니다(MAE 3.045 vs 3.036). 이 값은 당시 API 기준 비교이며 현재 모델이나 실제 탑승 성능의 검증 결과가 아닙니다. 서비스는 라이트 모델을 사용합니다.

|---|---|---|
| `route`, `stop`, `stop_name` | sb02, 32, 녹십자약국 | 노선·정류장 |
| `plate` | 서울70사6419 | 차량번호 |
| `stops_away`, `eta_sec` | 0, 100 | 몇 정류장 전, 도착까지 초 |
| `eta2_sec` | 240 또는 null | 둘째 버스 도착까지 초. 다음 버스 ETA만 제공하며 확률은 없음 |
| `r_now` | 39 또는 null | API 제공 인원. 인원형이 아니면 null. 예측 보류와 원본 데이터 유효성은 별도로 판단 |
| `load_pred` | 42.5 또는 null | 도착 예상 인원. 보류 시 null |
| `load_10`, `load_90` | 39, 49 또는 null | 예상 범위. 보류 시 모두 null |
| `p_board` | 0.99 또는 null | API 기준 계산값. 보류 시 null |
| `level` | 여유 있음 | 화면에 보여줄 단계 |
| `reason` | P 0.99 ≥ 기준 0.99 | 단계를 고른 근거 |
| `updated` | 13:11:33 | 버스 정보를 받은 시각(KST) |

### 단계 (기능흐름도 F-04 순서대로 판단)
1. **확률 보류** — 수업 없는 날 / 데이터 부족·지연 / 등록 안 된 차량 / 입력 불량 / 모델 검증 정책 불일치
   (11-04: '판단하기 일러요'와 정원 초과 보류는 없앰 — 범위가 넓어도·만차여도 확률로 안내)
2. **여유 있음** — P 가 칸별 기준 이상. 기준은 "여유라고 보여줬을 때 API 인원으로 계산한 탑승 가능 비율 ≥ 97% (수업 직전 98%)"를 지킨 가장 낮은 P

   | | 바로 앞 | 1~2정류장 전 | 3정류장+ 전 |
   |---|---|---|---|
   | 평소 | P ≥ 0.80 | P ≥ 0.80 | P ≥ 0.80 |
   | 수업 직전 | P ≥ 0.94 | P ≥ 0.87 | P ≥ 0.89 |
3. **어려울 수 있음** — P ≤ 0.3
4. **빠듯함** — 그 사이

위 기준은 저장소의 11/4 생성 모델(11/3까지 30일 학습)의 `meta.json` 값입니다. 운영 31일 모델의 임계값은 2026-11-05 기준 미확인입니다.

"수업 직전" = 버스 도착 10~35분 뒤 시작하는 강좌(대면+BL)가 40개 이상. 기준은 모델을 다시 학습할 때마다 새로 정해집니다(`models/lite/meta.json` 의 `thresholds`).

`config/boarding_policy.json`은 14대를 API 기반 실용 정원으로 등록하고 켜 둡니다(근거는 API 기반, 현장 대조는 11주차). 정원표를 바꾸면 모델을 다시 export 해야 확률이 열립니다. 예측 인원·확률 필드는 보류 시 null이며, 원본 `r_now`는 데이터 상태에 따라 별도로 처리합니다.  날짜 포함 시각·원본 상태·보류 원인을 추가했습니다. [API 계약과 검증 후 재개 절차](docs/CAPACITY_FIX_20261102.md)를 따릅니다. 기존 CSV는 원본으로 재생성해야 하며 메타데이터 버전만 수동 변경하지 않습니다.

### 백엔드에서 쓰기
운영 서버(**161.33.132.80**, 수집기와 같은 서버)에서는 **`predict_latest`** 를 씁니다.
```python
import sys; sys.path.insert(0, "/home/ubuntu/hanjari-releases/practical-20261105-v9/hanjari-ml/src")
import serve
res = serve.predict_latest(3)        # 최신 저장 스냅샷 사용, 외부 버스 API 호출 없음
```
- **API 한도를 쓰지 않아** 사용자가 몰려도 괜찮습니다. 스냅샷이 180초보다 오래되면 확률을 보류합니다. 화면은 운행 시간 아님·수집 지연·해당 정류장 정보 없음을 구분합니다.
- 모델은 처음 부를 때 한 번 읽고 메모리에 둡니다. 사용량은 모델·환경에 따라 달라집니다. 매일 01:00 마감이 새 모델로 바꾸므로 **`hanjari-daily` 가 끝나자마자 백엔드(`hanjari-web`)를 재시작**합니다(ExecStartPost). 고정 시각(03:00) 재시작은 재학습이 길어지면 새 모델보다 먼저 돌아 하루 늦은 모델을 쓰게 돼 10-18 에 없앴습니다.
- 서버가 아닌 곳(노트북)에서는 `predict_live(3)`(API 4건 호출, 키 필요) 또는 `predict_live(3, log_dir=serve.SAMPLE)`(키 없이).

### 서버 한 대 구성 (1GB)
```
nginx      공개 HTTPS :443 → 내부 127.0.0.1:8000
FastAPI    API + React 빌드 화면 + 예측 모델
수집기     버스 API 수집
새벽 학습  매일 01:00 시작, 제한 설정은 운영 systemd 사본 참조
```
- 프론트 빌드(`npm run build`)는 **서버에서 하지 않기**(메모리 1GB 넘게 씀 → 수집기까지 죽을 수 있음). 노트북·GitHub Actions 에서 빌드해 `dist/` 만 올림.
- 공개 서비스는 HTTPS 443이며 80은 일반 요청의 HTTPS 이동 및 인증서 검증에 사용합니다. **8000은 내부 전용**입니다. 현재 설정과 포트 복원 백업은 [운영 구성](../deployment/README.md)을 참고합니다.

## 8. 운영 (MLOps)

버스가 도착하면 정답(도착 때 재차)이 자동으로 생기므로, **매일 채점 → 재학습 → 좋을 때만 교체**를 사람 없이 돌립니다.

```
매일 01:00 (수집기가 쉬는 새벽, 오라클)  src/daily.py
  ① 데이터 점검   어제 로그: 스냅샷 수 · 07~22시와 노선별 운행 시간(첫·막차 ±10분)이 겹치는 점검창의 최대 공백 · API 오류 응답 → OK / WARN / FAIL(학습 안 함)
  ② 어제 성적     지금 서비스 중인 모델로 어제를 채점 → reports/daily_metrics.csv
  ③ 재학습        어제까지 데이터로 후보 모델 → models/versions/YYYYMMDD/
  ④ 합격 판정     날짜분할 오차가 지금 모델의 1.1배 이하 · '여유' 후 API 기준 계산 탑승 ≥ 97% · 자체 점검 통과
  ⑤ 배포         합격이면 models/lite 교체 (이전 버전은 versions/ 에 남음)
  ⑥ 정리         원본 로그는 최근 3일만 폴더로, 그 전은 tar.gz 압축(223MB → 15MB/일) · 모델 버전은 최근 7개 · 디스크 5GB 미만이면 경고
  요약           reports/daily/YYYYMMDD.md
```
- 저장 공간: 정리 없이 하루 약 265MB(37GB 를 약 5개월에 다 씀) → 정리 후 약 17MB/일.
- 압축된 날은 학습 데이터 캐시(`data/processed/days/`)로 그대로 이어 붙입니다(압축 전후 학습 데이터 바이트 동일 확인). 피처를 바꿔 전부 다시 만들 때만 `tar xzf archive/YYYYMMDD.tar.gz -C api_logs` 로 풀어서 씁니다.
- 학습 데이터는 **증분**으로 만듭니다(`data/processed/days/` 에 날짜별 저장, 새로 들어온 날만 계산하고 날짜별 결과를 순차 기록; 메모리 사용량을 고정 수치로 보장하지 않음).
- 오라클(메모리 1GB)에서는 수집기를 지키기 위해 메모리 상한(500~650MB)·CPU 1코어·최저 우선순위로 실행합니다.

### 완전 자동 운영 — [`ops/RUNBOOK.md`](ops/RUNBOOK.md)
| 무엇 | 언제 | 하는 일 |
|---|---|---|
| `hanjari-collect` | 24시간 | 버스 API 수집 (꺼지면 30초 뒤 자동 재시작) |
| `hanjari-watchdog.timer` | 10분마다 | 새 데이터 10분 넘게 없으면 수집기 재시작 + 알림, API 오류(키·한도)·디스크 부족 알림 |
| `hanjari-daily.timer` | 매일 01:00 KST | 위 ①~⑥ + 결과 알림(이상 있으면 ⚠) |
| `hanjari-fail@` | 작업 실패 시 | 실패 알림 |
| `hanjari-web` | 24시간 | 백엔드 FastAPI `127.0.0.1:8000`(API + 화면, 운영 웹 릴리스 v9). 하루 마감이 끝나면 재시작해 새 모델을 읽음 — 유닛 `ops/systemd/hanjari-web.service` |
- 알림: 항상 `reports/alerts.log`, 디스코드 웹훅(`HANJARI_WEBHOOK`)을 넣으면 채널로.
- 되돌리기: `python src/daily.py rollback` (바로 전 모델 버전으로).
- **새 서버 설치**: `ops/install.sh`는 기존 MLOps 설치 템플릿입니다. 현재 모노레포 경로와 운영 설정을 대조해야 하며 웹 릴리스·HTTPS·방화벽 전체를 자동 구성하는 절차가 아닙니다. [RUNBOOK](ops/RUNBOOK.md)을 따릅니다.

### DVC (데이터·모델 버전)
```bash
dvc repro          # 로그 → 학습 데이터 → 라이트 모델 (바뀐 단계만)
dvc metrics show   # 모델 성적(날짜 분할)
dvc push / pull    # 학습 데이터를 저장소(오라클 서버)와 주고받기 — 오라클 접속 권한 필요
```
이 사본에는 DVC 원격 설정과 캐시가 없어 `dvc push` / `dvc pull` 전에 별도 저장소 연결이 필요합니다.

`dvc.yaml` 에 단계, `dvc.lock` 에 "어떤 로그·코드로 만든 어떤 결과인지"가 기록되고 git 커밋과 함께 버전이 됩니다.
예전 버전 되돌리기: `git checkout <커밋> && dvc checkout`. 라이트 모델은 팀원이 바로 쓰도록 git 에 그대로 둡니다(DVC 는 기록만).

## 10. 지키는 규칙
- 조회 시점에 알 수 있는 정보만 입력으로 씁니다. 도착 이후 정보는 정답으로만.
- 평가는 **날짜 단위**로 나눕니다(같은 날이 학습·평가에 섞이면 점수가 부풀려짐).
- 개인정보는 저장하지 않습니다. API 키는 `.env` 에만(레포에 없음).
- 원본 데이터(`data/raw`, `data/api_logs`)는 수정하지 않습니다.
