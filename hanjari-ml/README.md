## 0. 브랜치 사용법 (팀원 먼저 읽기)

작업마다 브랜치가 있고, **최신 main 에서 시작해 담당 폴더 중심으로** 작업합니다. 자세한 절차는 [공통 협업 안내](../CONTRIBUTING.md)를 따릅니다.

> ⛔ **`main` 에 직접 push 하지 마세요.** main 은 모두의 작업이 합쳐진 최종본(서비스·발표 기준)입니다.
> 합치고 싶으면 **Pull Request 를 열고**, **팀원 한 명 이상이 검토**하고 화면·서버·예측 연결을 확인한 뒤 Merge 합니다.
> 각 브랜치에서 할 일·작업 순서는 아래 표의 작업 안내에 있어요.

| 브랜치 | 사람 | 작업 | 작업 폴더 |
|---|---|---|---|
| `main` | 모두 | 합쳐진 최종본 (직접 push 금지) | — |
| `ai/prediction-improvement` | 최지용 | [예측 모델 개선](../docs/work/ai/README.md) | `hanjari-ml/` |
| `be/boarding-record` | 유민준 | [익명 탑승 결과 기록](../docs/work/backend/README.md) | `hanjari-web/backend/` |
| `fe/ui-improvement` | 서재현 | [화면 사용성 개선](../docs/work/frontend-ui/README.md) | `hanjari-web/frontend/` |
| `fe/status-guidance` | 황정원 | [오류·지연 안내 개선](../docs/work/frontend-status/README.md) | `hanjari-web/frontend/` |

모든 브랜치에 전체 코드가 들어 있습니다. 프론트엔드 두 브랜치는 같은 폴더를 쓰므로, **같은 파일을 고칠 때는 수정 범위를 먼저 상의**하세요.

```bash
git clone https://github.com/EarlyAccess-HanJari/HanJari.git && cd HanJari
git fetch origin
git switch --track origin/ai/prediction-improvement   # ① 내 브랜치로 (처음 한 번, 이후엔 git switch 브랜치명)
# ... hanjari-ml/ 안에서 작업 ...
git add hanjari-ml && git commit -m "무엇을 했는지 한 줄"
git push                                              # ② 내 브랜치에 올리기
# ③ GitHub → Pull requests → New → base: main ← compare: ai/prediction-improvement → Create (검토 후 Merge)
git fetch origin && git merge origin/main             # ④ 다른 사람 작업을 내 브랜치로 가져오기 (내 변경을 먼저 커밋)
```
- **다른 담당 폴더를 고칠 때는 해당 담당자와 먼저 상의하기.** 브랜치에서 지운 파일은 합칠 때 main 에서도 지워집니다.
- API 키·비밀번호는 커밋 금지(`.env` 에만).
- 응답 항목을 바꾸면 프론트엔드·백엔드·AI 담당자가 먼저 합의합니다. 백엔드가 AI 예측을 부를 때는 아래 7절 "결과 형식" 대로 `serve.predict_live` 를 씁니다.
- 운영 서버의 파일 수정·설치·재시작·배포는 별도 합의 없이 하지 않습니다.

## 2. 무엇을 예측하나

대상 정류장 6곳 (등교 방향, 노선 순서대로 같은 버스가 지나감):

| 노선 | 노선ID | 정류장(순번) |
|---|---|---|
| 성북02 | 107900003 | 한성대입구역5번출구(30) → 한성대입구역2번출구(31) → 녹십자약국(32) |
| 종로03 | 100900010 | 동대문역.흥인지문(19) → 동묘앞역(20) → 창신역4번출구(23) → 한성대후문(28) 하차 |

"탔나/못 탔나"는 어디에도 기록되지 않습니다. 그래서 **정답이 자동으로 생기는 문제로 바꿨습니다.**

```
탑승 가능 ⇔ 남은 자리 > 내 앞 대기 인원
남은 자리 = 정원 C − (도착 때 재차 y − 그 정류장 하차 D)
P(탑승) = P( y − D ≤ C − N − 1 )        N = 내 앞 대기 인원(사용자 입력)
```
- **모델이 맞히는 것 = 버스가 내 정류장에 도착했을 때의 재차 인원 y 의 분포.**
- y 는 서울시 버스 API 가 주는 재차 인원(`reride_Num`)이라, 버스가 도착할 때마다 정답이 자동으로 쌓입니다.
- 정원 C: 차종별 잠정값(법정+입석 여유)과 실제로 관측된 최대 재차 중 큰 값. 현재 성북02 작은 차 40·큰 차 70, 종로03 55.
- 하차 D: 공공 CSV 의 시간대별 평균.

## 5. 모델

**구조: 규칙 + XGBoost 가 규칙의 오차를 학습**
```
규칙   = 지금 재차 + 남은 정류장들의 과거 평균 순승차(CSV) + 지금 정차 중인 정류장의 미반영 몫
예측 y = 규칙 + XGB(피처)          ← XGB 는 "규칙이 얼마나 틀리는지"만 배움
```
- **점 예측**: 절대오차(MAE) 목표 XGB.
- **확률**: 5~95% 분위수 9개를 한 번에 내는 XGB → 그 분포로 P(탑승) 계산.
- **바로 앞(0정류장 전)**: 버스가 그 정류장에 서 있으면 재차가 아직 안 바뀐 상태(재차는 **출발할 때** 갱신됨) → 전용 작은 모델 + 실제 오차 분포.
- 설정: 깊이 5 · 트리 300 · 학습률 0.06, **수업 있는 날(월~토, 공휴일 제외)만 학습** (09-30 깊이 2→5, 10-01 평일만 MAE 3.09→2.84, 서버 1GB 에 맞춰 가볍게: 정확도 같고 학습 메모리 609→472MB·예측 722→406MB).
- 재차는 0 이상·정원 이하로 자름.

**라이트 모델 (이 레포의 `models/lite/`)** — 버스 API 를 **지금 1번** 부른 결과로 계산되는 피처만 씁니다(28개).

| 묶음 | 피처 |
|---|---|
| 위치·재차 | 몇 정류장 전, ETA, 지금 재차, 차종·정원, 채움 비율 |
| 뒤차 | 둘째 버스 ETA·재차, 두 버스 간격 |
| 노선 전체 | 지금 노선 위 모든 버스 평균 재차 |
| 과거 평균 | 남은 구간 CSV 평균 순승차, 하차, 이전 수집일 같은 시간대 실측 |
| 수업 | 버스 도착 10~35분 뒤 시작하는 강좌 수, 다음 큰 수업까지 분, 수업 직전 여부 |
| 달력 | 요일, 학기/방학, 시험, 공휴일 |
| 위치 API | 정차 중인지, 구간 진행률, 정차 중 미반영 몫 |

오라클 수집 이력(최근 60~90분 다른 버스들의 승차 흐름 등 10개)까지 쓰는 **전체 모델과 정확도가 같았습니다**(MAE 3.045 vs 3.036).
그래서 서비스는 라이트 모델로 충분합니다.

| **라이트 모델** | **3.0명** | **0.034** | **98.6%** |

## 7. 결과 형식 (`predict_live(n_ahead)`)

`n_ahead`: 내 앞 대기 인원 0~40 정수. 반환: 정류장마다 dict 한 개(지금 오는 첫 버스).

| 항목 | 예 | 뜻 |
|---|---|---|
| `route`, `stop`, `stop_name` | sb02, 32, 녹십자약국 | 노선·정류장 |
| `plate` | 서울70사6419 | 차량번호 |
| `stops_away`, `eta_sec` | 0, 100 | 몇 정류장 전, 도착까지 초 |
| `r_now` | 39 | 지금 타고 있는 인원 |
| `load_pred` | 42.5 | 내 정류장 도착 때 예상 인원 |
| `load_10`, `load_90` | 39, 49 | 예상 범위(10~90%) |
| `p_board` | 0.99 | 탈 확률 |
| `level` | 여유 있음 | 화면에 보여줄 단계 |
| `reason` | P 0.99 ≥ 기준 0.99 | 단계를 고른 근거 |
| `updated` | 13:11:33 | 버스 정보를 받은 시각(KST) |

### 단계 (기능흐름도 F-04 순서대로 판단)
1. **확률 보류** — 수업 없는 날(일요일·공휴일 — 아직 검증 전) / 그 시간대·거리에 기준을 정할 데이터가 부족
2. **판단하기 일러요** — 예상 범위(10~90%)가 20명보다 넓음
3. **여유 있음** — P 가 칸별 기준 이상. 기준은 "여유라고 보여줬을 때 실제로 탄 비율 ≥ 97% (수업 직전 98%)"를 지킨 가장 낮은 P

   | | 바로 앞 | 1~2정류장 전 | 3정류장+ 전 |
   |---|---|---|---|
   | 평소 | P ≥ 0.80 | P ≥ 0.80 | P ≥ 0.80 |
   | 수업 직전 | P ≥ 0.92 | 표시 안 함 | 표시 안 함 |
4. **어려울 수 있음** — P ≤ 0.3
5. **빠듯함** — 그 사이

"수업 직전" = 버스 도착 10~35분 뒤 시작하는 강좌(대면+BL)가 40개 이상. 기준은 모델을 다시 학습할 때마다 새로 정해집니다(`models/lite/meta.json` 의 `thresholds`).

### 백엔드에서 쓰기
운영 서버(**161.33.132.80**, 수집기와 같은 서버)에서는 **`predict_latest`** 를 씁니다.
```python
import sys; sys.path.insert(0, "/home/ubuntu/hanjari-ml/src")
import serve
res = serve.predict_latest(3)        # 수집기가 방금(27초 이내) 받은 스냅샷으로 — 버스 API 호출 없음, 약 1초
```
- **API 한도를 쓰지 않아** 사용자가 몰려도 괜찮습니다. 스냅샷이 3분보다 오래되면(수집 중단·새벽) 전부 '확률 보류'.
- 모델은 처음 부를 때 한 번 읽고 메모리에 둡니다(약 400MB). 매일 01:00 마감이 새 모델로 바꾸므로 **`hanjari-daily` 가 끝나자마자 백엔드(`hanjari-web`)를 재시작**합니다(ExecStartPost). 고정 시각(03:00) 재시작은 재학습이 길어지면 새 모델보다 먼저 돌아 하루 늦은 모델을 쓰게 돼 10-18 에 없앴습니다.
- 서버가 아닌 곳(노트북)에서는 `predict_live(3)`(API 4건 호출, 키 필요) 또는 `predict_live(3, log_dir=serve.SAMPLE)`(키 없이).

### 서버 한 대 구성 (1GB)
```
nginx      프론트 정적 파일(React 빌드 dist/) + /api → FastAPI     ~10MB
FastAPI    백엔드 + 예측 모델                                       ~400MB
수집기     버스 API 수집                                            ~30MB
새벽 학습  01:00~02:30, 메모리 상한 650MB                           ~470MB  (+ 스왑 2GB)
```
- 프론트 빌드(`npm run build`)는 **서버에서 하지 않기**(메모리 1GB 넘게 씀 → 수집기까지 죽을 수 있음). 노트북·GitHub Actions 에서 빌드해 `dist/` 만 올림.
- 웹 접속용 80(필요하면 443) 포트를 **Oracle 콘솔 보안 목록과 서버 iptables 두 곳 모두** 열어야 함.

## 8. 운영 (MLOps)

버스가 도착하면 정답(도착 때 재차)이 자동으로 생기므로, **매일 채점 → 재학습 → 좋을 때만 교체**를 사람 없이 돌립니다.

```
매일 01:00 (수집기가 쉬는 새벽, 오라클)  src/daily.py
  ① 데이터 점검   어제 로그: 스냅샷 수 · 07~22시 최대 공백 · API 오류 응답 → OK / WARN / FAIL(학습 안 함)
  ② 어제 성적     지금 서비스 중인 모델로 어제를 채점 → reports/daily_metrics.csv
  ③ 재학습        어제까지 데이터로 후보 모델 → models/versions/YYYYMMDD/
  ④ 합격 판정     날짜분할 오차가 지금 모델의 1.1배 이하 · '여유' 후 실제 탑승 ≥ 97% · 자체 점검 통과
  ⑤ 배포         합격이면 models/lite 교체 (이전 버전은 versions/ 에 남음)
  ⑥ 정리         원본 로그는 최근 3일만 폴더로, 그 전은 tar.gz 압축(223MB → 15MB/일) · 모델 버전은 최근 7개 · 디스크 5GB 미만이면 경고
  요약           reports/daily/YYYYMMDD.md
```
- 저장 공간: 정리 없이 하루 약 265MB(37GB 를 약 5개월에 다 씀) → 정리 후 약 17MB/일.
- 압축된 날은 학습 데이터 캐시(`data/processed/days/`)로 그대로 이어 붙입니다(압축 전후 학습 데이터 바이트 동일 확인). 피처를 바꿔 전부 다시 만들 때만 `tar xzf archive/YYYYMMDD.tar.gz -C api_logs` 로 풀어서 씁니다.
- 학습 데이터는 **증분**으로 만듭니다(`data/processed/days/` 에 날짜별 저장, 새로 들어온 날만 계산 → 메모리 약 235MB 로 일정).
- 오라클(메모리 1GB)에서는 수집기를 지키기 위해 메모리 상한(500~650MB)·CPU 1코어·최저 우선순위로 실행합니다.

### 완전 자동 운영 — [`ops/RUNBOOK.md`](ops/RUNBOOK.md)
| 무엇 | 언제 | 하는 일 |
|---|---|---|
| `hanjari-collect` | 24시간 | 버스 API 수집 (꺼지면 30초 뒤 자동 재시작) |
| `hanjari-watchdog.timer` | 10분마다 | 새 데이터 10분 넘게 없으면 수집기 재시작 + 알림, API 오류(키·한도)·디스크 부족 알림 |
| `hanjari-daily.timer` | 매일 01:00 KST | 위 ①~⑥ + 결과 알림(이상 있으면 ⚠) |
| `hanjari-fail@` | 작업 실패 시 | 실패 알림 |
| `hanjari-web` | 24시간 | 백엔드 FastAPI :8000(API + 화면, 코드는 `pm/jeongwon` 의 backend/·frontend/). 하루 마감이 끝나면 재시작해 새 모델을 읽음 — 유닛 `ops/systemd/hanjari-web.service` |
- 알림: 항상 `reports/alerts.log`, 디스코드 웹훅(`HANJARI_WEBHOOK`)을 넣으면 채널로.
- 되돌리기: `python src/daily.py rollback` (바로 전 모델 버전으로).
- **새 서버 설치: `bash ops/install.sh` 한 번**(스왑·Python 환경·수집기·타이머·로그 정리까지). 키와 공공 CSV 표(`dvc pull`)만 준비.

### DVC (데이터·모델 버전)
```bash
dvc repro          # 로그 → 학습 데이터 → 라이트 모델 (바뀐 단계만)
dvc metrics show   # 모델 성적(날짜 분할)
dvc push / pull    # 학습 데이터를 저장소(오라클 서버)와 주고받기 — 오라클 접속 권한 필요
```
`dvc.yaml` 에 단계, `dvc.lock` 에 "어떤 로그·코드로 만든 어떤 결과인지"가 기록되고 git 커밋과 함께 버전이 됩니다.
예전 버전 되돌리기: `git checkout <커밋> && dvc checkout`. 라이트 모델은 팀원이 바로 쓰도록 git 에 그대로 둡니다(DVC 는 기록만).

## 10. 지키는 규칙
- 조회 시점에 알 수 있는 정보만 입력으로 씁니다. 도착 이후 정보는 정답으로만.
- 평가는 **날짜 단위**로 나눕니다(같은 날이 학습·평가에 섞이면 점수가 부풀려짐).
- 개인정보는 저장하지 않습니다. API 키는 `.env` 에만(레포에 없음).
- 원본 데이터(`data/raw`, `data/api_logs`)는 수정하지 않습니다.
