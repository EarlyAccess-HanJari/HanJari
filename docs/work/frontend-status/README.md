# 프론트엔드 · 오류와 지연 안내 개선

담당: **서재현** · 이전 구현: 황정원

사용자가 버스가 없는 상황, 자료가 오래된 상황, 서버 연결 문제를 구분하고, 정상 동작을 오류로 오해하지 않게 하는 것이 목표입니다.

## 현재 구현

| 상황 | 안내 |
| --- | --- |
| 운행 시간 아님 | "지금은 버스가 다니지 않아요" |
| 수집 지연 | "버스 정보 갱신이 늦어지고 있어요" |
| 이 정류장 정보 없음 | "이 정류장 버스 정보가 없어요" |
| 자료 180초 초과 | 도착 시간과 확률을 숨기고 "버스 정보가 늦어지고 있어요" |
| 도착 예정 시각 지남 | "새 도착 정보를 확인하고 있어요" |
| 인원을 바꾼 뒤 응답 대기 | 이전 확률을 숨기고 "N명 기준으로 다시 계산하고 있어요". 3초가 넘으면 오래 걸린다고 안내 |
| 인원을 바꾼 요청 실패 | "N명 기준 확률을 못 받았어요"와 다시 시도 |
| 일요일·공휴일 | "오늘은 탑승 예측을 쉬어요". 도착 시간과 지금 인원은 그대로 |
| 첫 조회 오류 | 카드 안에 안내와 다시 시도. 60초 뒤 자동 재시도 |
| 새로고침만 실패 | 화면을 유지하고 상태 줄에 "마지막으로 받은 정보"라고 안내 |
| 인터넷 끊김 | 받아 둔 도착 정보와 입력칸을 유지. 받아 둔 정보가 없으면 연결 확인 안내 |

아이콘은 실제 연결 실패에만 끊김 아이콘을 쓰고, 지연은 시계, 정보 없음은 안내, 운행 시간 아님은 달을 씁니다.

## 남은 작업

기한은 WBS의 이용 불편 개선(5.3, 11/14)과 피드백·오류 반영(5.10, 11/26)을 따릅니다.

### 대체 안내 카드 (담당 협의)

서버는 수집이 3분 넘게 끊기면 `fallback`을 함께 줍니다(PR #20). 지금 화면은 이 항목을 무시하고 "버스 정보가 늦어지고 있어요"만 보여 줍니다. 응답 형식과 문구안은 [대체 안내 문서](../../../hanjari-ml/docs/OUTAGE_FALLBACK_20261105.md)에 있습니다. PR #20에는 담당이 황정원으로 적혀 있으니 화면 개편에 맞춰 담당을 정합니다.

### 현장에서 확인할 것

교수님 피드백("오류가 나는 것처럼 보임")에서 나온 작업입니다. 위 안내가 실제로 오류처럼 보이지 않는지 11/9~11/13 현장 기록과 11/16~11/21 사용성 평가에서 확인합니다.

서버에서 구분할 수 없는 상태는 화면에서 임의로 판단하지 않습니다.

## 예외 화면 확인

`hanjari-web/frontend`에서 `VITE_MOCK=1`로 실행한 뒤 주소 뒤에 값을 붙입니다. 목업 모드에서만 동작합니다.

```sh
npm ci
npm run dev
```

- `?scenario=curve`: 저장된 모델 값으로 앞 0~40명을 눌러 보기
- `?scenario=approach-1`~`approach-7`: 버스가 다가올 때 동묘앞역 문구 변화(대부분 설명용 값)
- `?scenario=passed`: 버스가 막 지나감
- `?scenario=holiday`: 일요일·공휴일
- `?scenario=held`: 이 버스만 예측 보류
- `?scenario=down`: 서버 연결 실패
- `?scenario=error`: 서버 오류
- `?scenario=slow`: 응답 지연
- `?scenario=stale`: 오래된 정보
- `?scenario=night`: 운행 시간 안내
- `?scenario=checking`: 도착 확인 중
- `?scenario=nocount`: 차내 인원 없음
- `?scenario=wide`: 판단 유보. 현재 서버는 이 단계를 내지 않습니다.

## 테스트와 PR

테스트와 빌드는 [화면 사용성 개선](../frontend-ui/README.md#테스트와-빌드)과 같습니다. 목업 화면을 운영 화면처럼 설명하지 않도록 캡처에 상황과 입력값을 적습니다.

[공통 협업 안내](../../../CONTRIBUTING.md)에 따라 PR을 만들고, 확인한 상황·입력값·결과를 적습니다. API 변경이 있으면 유민준과 함께 확인합니다.
